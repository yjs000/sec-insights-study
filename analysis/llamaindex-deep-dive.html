전역 설정 (Settings)

backend/app/llama_index_settings.py

가장 먼저 읽어야 하는 이유: 이 파일이 "어떤 LLM, 어떤 임베딩 모델, 어떤 청크 크기를 쓸지"를 앱 전체에 딱 한 번 세팅합니다. 이후 나오는 모든 인덱스/쿼리엔진 코드는 이 설정을 몰래 상속받아 씁니다.

from llama_index.core import Settings
from llama_index.core.settings import _Settings
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding, OpenAIEmbeddingMode, OpenAIEmbeddingModelType
from app.core.config import settings
from llama_index.core.node_parser import SentenceSplitter

from app.chat.constants import (
    NODE_PARSER_CHUNK_OVERLAP,
    NODE_PARSER_CHUNK_SIZE,
)
import 정리:
  • Settings — LlamaIndex의 전역 설정 객체. 예전 버전에서는 ServiceContext라는 걸 매번 함수마다 넘겨줘야 했는데, 지금은 이 Settings에 한 번만 값을 넣어두면 어디서든 자동으로 읽힙니다. (파이썬의 전역 싱글턴 패턴)
  • OpenAI (llms.openai) — LLM 래퍼 클래스. "질문에 답을 생성하는" 모델(예: gpt-4)을 감싸는 객체.
  • OpenAIEmbedding — 텍스트를 벡터(숫자 배열)로 바꾸는 임베딩 모델 래퍼. LLM과는 별개 모델입니다 (LLM=답변 생성용, Embedding=검색용).
  • SentenceSplitter — 긴 문서를 문장 단위를 존중하면서 일정 크기로 잘라주는 "청크 분할기(Node Parser)".
  • app.core.config.settings는 이 프로젝트 자체의 환경변수 설정(우리 앱의 config)이고, 위의 llama_index.core.Settings는 LlamaIndex 라이브러리의 전역 설정입니다. 이름이 겹쳐서 헷갈리기 쉬우니 주의하세요.
def _setup_llama_index_settings() -> _Settings:
    Settings.llm = OpenAI(
        model=settings.OPENAI_CHAT_LLM_NAME,
        api_key=settings.OPENAI_API_KEY
    )
    Settings.embed_model = OpenAIEmbedding(
        mode=OpenAIEmbeddingMode.SIMILARITY_MODE,
        model_type=OpenAIEmbeddingModelType.TEXT_EMBED_3_SMALL,
        api_key=settings.OPENAI_API_KEY,
    )
    Settings.node_parser = SentenceSplitter(
        chunk_size=NODE_PARSER_CHUNK_SIZE,
        chunk_overlap=NODE_PARSER_CHUNK_OVERLAP,
    )
    return Settings
  • Settings.llm = OpenAI(...) — "앞으로 답변 생성이 필요할 때는 이 OpenAI 모델을 써라"고 전역에 등록. 이후 코드 어디서도 llm=...을 명시적으로 넘기지 않으면 자동으로 이 값이 쓰입니다.
  • Settings.embed_model = OpenAIEmbedding(...) — 문서를 벡터DB에 저장할 때, 그리고 질문을 벡터로 바꿔 검색할 때 사용할 임베딩 모델. TEXT_EMBED_3_SMALL은 OpenAI의 저비용 임베딩 모델 이름.
  • Settings.node_parser = SentenceSplitter(chunk_size=512, chunk_overlap=10) — PDF를 512 토큰(대략 단어 300~400개) 단위로, 청크 사이 10 토큰씩 겹치게 잘라서 검색 정확도를 높입니다. (겹치게 자르는 이유: 문장이 청크 경계에서 잘려 의미가 끊기는 걸 방지)
  • 이 함수는 main.py의 start() 함수 안에서 서버가 뜨기 직전에 딱 한 번 호출됩니다. 그 이후로는 이 파일을 다시 볼 일이 없습니다 — "설정하고 잊기" 패턴.
핵심 포인트: LlamaIndex는 "이번 함수 호출에서만 쓸 LLM"을 매번 인자로 넘기는 대신, Settings라는 전역 변수에 한 번 박아두고 모든 인덱스/쿼리엔진이 암묵적으로 참조하게 만드는 구조입니다. 나중에 코드에서 llm= 인자가 안 보여도 당황하지 마세요 — Settings.llm이 쓰이고 있는 겁니다.

벡터 저장소 연결 (pgvector)

backend/app/chat/pg_vector.py

임베딩 벡터를 실제로 어디에 저장하는지 담당하는 파일. LlamaIndex의 VectorStore 추상 인터페이스를 Postgres(pgvector 확장)로 구현한 PGVectorStore를 커스터마이징합니다.

from llama_index.core.vector_stores.types import VectorStore
from llama_index.vector_stores.postgres import PGVectorStore
...

class CustomPGVectorStore(PGVectorStore):
    """
    Custom PGVectorStore that uses the same connection pool as the FastAPI app.
    """

    def _connect(self) -> None:
        self._engine = create_engine(self.connection_string)
        self._session = sessionmaker(self._engine)

        # Use our existing app engine and session so we can use the same connection pool
        self._async_engine = app_engine
        self._async_session = AppSessionLocal
  • VectorStore — LlamaIndex가 정의한 인터페이스(추상 클래스)입니다. "임베딩을 저장하고, 유사도 검색을 할 수 있으면" 무엇이든 VectorStore가 될 수 있습니다 (Pinecone, Chroma, Postgres, ...). 이 프로젝트는 PGVectorStore(공식 구현체)를 상속해서 커스터마이징합니다.
  • class CustomPGVectorStore(PGVectorStore) — 왜 상속해서 커스텀했나? 기본 구현은 자기가 알아서 새 DB 커넥션 풀을 만드는데, 이 FastAPI 앱은 이미 SQLAlchemy 커넥션 풀(app_engine)을 갖고 있으므로 벡터 저장소도 그 풀을 재사용하도록 _connect()를 오버라이드한 것입니다. (커넥션 풀 중복 생성 방지 = 리소스 절약)
  • 즉 이 클래스 자체는 LlamaIndex 개념이라기보다 "기존 FastAPI 인프라와 LlamaIndex를 접붙이는 접착제 코드"입니다.
    async def run_setup(self) -> None:
        global did_run_setup
        if did_run_setup:
            return
        self._initialize()
        async with self._async_session() as session:
            async with session.begin():
                statement = sqlalchemy.text("CREATE EXTENSION IF NOT EXISTS vector")
                await session.execute(statement)
                await session.commit()

        async with self._async_session() as session:
            async with session.begin():
                conn = await session.connection()
                await conn.run_sync(self._base.metadata.create_all)
        did_run_setup = True
  • CREATE EXTENSION IF NOT EXISTS vector — Postgres에 pgvector 확장을 활성화하는 SQL. 이게 있어야 Postgres가 벡터 컬럼 타입과 코사인/L2 유사도 연산을 지원합니다.
  • self._base.metadata.create_all — SQLAlchemy ORM 모델(임베딩을 저장할 테이블 스키마)을 실제 테이블로 생성. 즉 "임베딩 테이블이 없으면 만들어라"는 마이그레이션 겸 초기화 로직입니다.
  • did_run_setup 플래그로 앱 실행 중 한 번만 실행되게 막습니다. 이 함수는 main.py의 lifespan()에서 서버 시작 시 호출됩니다.
async def get_vector_store_singleton() -> VectorStore:
    global singleton_instance
    if singleton_instance is not None:
        return singleton_instance
    url = make_url(settings.DATABASE_URL)
    singleton_instance = CustomPGVectorStore.from_params(
        url.host, url.port or 5432, url.database, url.username, url.password,
        settings.VECTOR_STORE_TABLE_NAME,
    )
    return singleton_instance
  • 싱글턴 패턴 — 앱 전체에서 VectorStore 인스턴스를 딱 하나만 만들어 재사용합니다. 이 함수는 이후 engine.py, seed_storage_context.py 등 여러 곳에서 반복 호출되지만, 실제 인스턴스 생성은 최초 1회뿐입니다.
  • settings.VECTOR_STORE_TABLE_NAME — 임베딩이 저장될 Postgres 테이블 이름을 앱 설정값으로부터 가져옵니다.

핵심 파이프라인 (인덱스 로딩 → 도구 조립 → 에이전트 생성)

backend/app/chat/engine.py

이 프로젝트에서 가장 중요한 파일입니다. "PDF → 인덱스 → 도구 → 에이전트"로 이어지는 전체 파이프라인이 이 파일 하나에 다 들어 있습니다. 순서대로 함수 단위로 뜯어봅니다.

4-1. 문서를 내려받아 LlamaIndex Document로 변환

def fetch_and_read_document(
    document: DocumentSchema,
) -> List[LlamaIndexDocument]:
    with TemporaryDirectory() as temp_dir:
        temp_file_path = Path(temp_dir) / f"{str(document.id)}.pdf"
        with open(temp_file_path, "wb") as temp_file:
            with requests.get(document.url, stream=True) as r:
                r.raise_for_status()
                for chunk in r.iter_content(chunk_size=8192):
                    temp_file.write(chunk)
            temp_file.seek(0)
            reader = PDFReader()
            return reader.load_data(
                temp_file_path, extra_info={DB_DOC_ID_KEY: str(document.id)}
            )
  • 우리 DB에 저장된 document.url(S3에 있는 PDF 링크)에서 파일을 스트리밍으로 내려받아 임시 디렉터리에 저장합니다.
  • PDFReader — LlamaIndex의 Reader(로더)입니다. PDF 파일 경로를 넣으면 페이지별로 텍스트를 뽑아 Document 객체 리스트로 반환합니다. Reader는 LlamaIndex 생태계에서 "무엇이든 Document로 바꿔주는 어댑터" 역할(PDF, Notion, Slack, 웹페이지 등 수백 종류가 있습니다).
  • extra_info={DB_DOC_ID_KEY: str(document.id)} — 이게 핵심입니다. 생성되는 모든 Document(나중엔 쪼개진 Node에도 상속됨)에 메타데이터로 "이 문서는 db_document_id=xxx 다"라는 꼬리표를 붙입니다. 이 꼬리표 덕분에 나중에 "이 문서에서만 검색해라"는 필터링이 가능해집니다 (4-4 참고).

4-2. 문서 하나 → 쿼리 엔진 하나 (메타데이터 필터 포함)

def index_to_query_engine(doc_id: str, index: VectorStoreIndex) -> BaseQueryEngine:
    filters = MetadataFilters(
        filters=[ExactMatchFilter(key=DB_DOC_ID_KEY, value=doc_id)]
    )
    kwargs = {"similarity_top_k": 3, "filters": filters}
    return index.as_query_engine(**kwargs)
  • 주의: 이 프로젝트는 모든 문서의 청크를 같은 Postgres 테이블에 함께 저장합니다 (문서별로 테이블을 나누지 않음). 그래서 검색할 때 "이 문서의 청크만" 걸러내야 하는데, 그게 바로 MetadataFilters + ExactMatchFilter(key=DB_DOC_ID_KEY, value=doc_id)입니다.
  • index.as_query_engine(similarity_top_k=3, filters=filters) — VectorStoreIndex를 QueryEngine(질문→검색→답변 파이프라인)으로 변환하는 한 줄. similarity_top_k=3은 "가장 유사한 청크 3개만 가져와서 답변에 사용해라"는 뜻.
  • 즉 "문서 1개 = 논리적으로 격리된 쿼리 엔진 1개"라는 착시를 메타데이터 필터로 구현한 것입니다. 실제 벡터는 다 같은 테이블에 있습니다.

4-3. StorageContext 캐싱

@cached(
    TTLCache(maxsize=10, ttl=timedelta(minutes=5).total_seconds()),
    key=lambda *args, **kwargs: "global_storage_context",
)
def get_storage_context(
    persist_dir: str, vector_store: VectorStore, fs: Optional[AsyncFileSystem] = None
) -> StorageContext:
    logger.info("Creating new storage context.")
    return StorageContext.from_defaults(
        persist_dir=persist_dir, vector_store=vector_store, fs=fs
    )
  • @cached(TTLCache(...)) — 파이썬 cachetools 라이브러리의 데코레이터로, 이 함수 결과를 5분간 메모리에 캐싱합니다. StorageContext.from_defaults(persist_dir=..., fs=...)가 S3에서 인덱스 메타 파일들을 읽어오는 I/O 작업이라 비싸기 때문에, 매 요청마다 새로 만들지 않고 재사용합니다.
  • StorageContext.from_defaults(persist_dir, vector_store, fs) — S3(fs로 추상화됨)의 persist_dir 경로에서 기존에 저장된 docstore/index_store 메타데이터를 읽어와 StorageContext를 복원합니다. 처음 실행이라 S3에 아무것도 없으면 FileNotFoundError가 나며, 이는 호출부(4-4)에서 잡아서 새로 만듭니다.

4-4. 문서 목록 → {문서ID: 인덱스} 맵 만들기 (가장 복잡한 함수)

async def build_doc_id_to_index_map(
    callback_manager: CallbackManager,
    documents: List[DocumentSchema],
    fs: Optional[AsyncFileSystem] = None,
) -> Dict[str, VectorStoreIndex]:
    persist_dir = f"{settings.S3_BUCKET_NAME}"
    vector_store = await get_vector_store_singleton()
    try:
        try:
            storage_context = get_storage_context(persist_dir, vector_store, fs=fs)
        except FileNotFoundError:
            storage_context = StorageContext.from_defaults(vector_store=vector_store, fs=fs)
            storage_context.persist(persist_dir=persist_dir, fs=fs)
        index_ids = [str(doc.id) for doc in documents]
        indices = load_indices_from_storage(
            storage_context, index_ids=index_ids, callback_manager=callback_manager,
        )
        doc_id_to_index = dict(zip(index_ids, indices))
    except ValueError:
        # 인덱스가 아직 한 번도 만들어진 적 없는 경우 (신규 문서)
        storage_context = StorageContext.from_defaults(
            persist_dir=persist_dir, vector_store=vector_store, fs=fs
        )
        doc_id_to_index = {}
        for doc in documents:
            llama_index_docs = fetch_and_read_document(doc)
            storage_context.docstore.add_documents(llama_index_docs)
            index = VectorStoreIndex.from_documents(
                llama_index_docs,
                storage_context=storage_context,
                callback_manager=callback_manager,
            )
            index.set_index_id(str(doc.id))
            index.storage_context.persist(persist_dir=persist_dir, fs=fs)
            doc_id_to_index[str(doc.id)] = index
    return doc_id_to_index
  • 큰 그림: "이미 인덱싱된 문서면 불러오고(load), 처음 보는 문서면 새로 만든다(build)"는 로드-or-생성(load-or-build) 패턴입니다.
  • try 블록 (로드 경로): load_indices_from_storage(storage_context, index_ids=[...]) — 이전에 index.set_index_id(doc_id)로 저장해둔 인덱스를, 같은 ID로 다시 불러옵니다. 문서 ID를 인덱스 ID로 그대로 쓰는 설계라 "이 문서 ID의 인덱스를 줘"라는 조회가 자연스럽게 됩니다.
  • except ValueError (신규 생성 경로): 저장소에 해당 index_id가 없으면 load_indices_from_storage가 ValueError를 던집니다. 이때 진짜로 처음부터 인덱스를 만듭니다:
    1. fetch_and_read_document(doc)로 PDF → Document 리스트 (4-1)
    2. storage_context.docstore.add_documents(...) — 원문 청크 원본을 docstore(메타 저장소)에 등록
    3. VectorStoreIndex.from_documents(docs, storage_context=...) — 여기서 실제로 청크 분할(SentenceSplitter) → 임베딩(OpenAIEmbedding) → pgvector 저장이 한 번에 일어남 (Settings에 등록된 값들이 암묵적으로 쓰임 — 파일 1 참고!)
    4. index.set_index_id(str(doc.id)) — "이 인덱스의 이름표는 문서ID다"라고 지정
    5. index.storage_context.persist(persist_dir, fs) — 인덱스 메타를 S3에 저장해서 다음 요청부턴 로드 경로를 타게 함
  • 이 함수는 대화(conversation)에 첨부된 문서들에 대해 매번 호출되지만, 이미 인덱싱된 문서라면 로드만 하면 되므로 (그리고 get_storage_context가 5분 캐싱되므로) 실제로는 꽤 빠릅니다.

  • {{context_str}}, {{query_str}} — 이건 파이썬 f-string의 {{ }} 이스케이프입니다. f-string으로 doc_titles는 지금 채워 넣고, context_str/query_str은 나중에 LlamaIndex가 채워 넣을 자리이므로 {{{{ }}}}처럼 이중 중괄호로 이스케이프한 것입니다. 즉 이 템플릿엔 이중 치환이 있습니다: 1) 지금 파이썬 f-string이 doc_titles를 채움, 2) 나중에 LlamaIndex 내부에서 context_str/query_str을 채움.
  • 이렇게 커스텀 프롬프트를 쓰는 이유: 기본 프롬프트는 범용적이라, "이건 SEC 재무제표 문서다", "사전 지식 말고 반드시 주어진 컨텍스트만 근거로 답하라" 같은 도메인 특화 지시가 없습니다. 이걸 넣으면 환각(hallucination)이 줄고 답변이 더 근거 있게 나옵니다.
  • get_response_synthesizer(...) — LlamaIndex가 제공하는 팩토리 함수로, 위 두 템플릿을 넣은 BaseSynthesizer 구현체(기본은 CompactAndRefine 계열)를 만들어 돌려줍니다. 이 결과가 파일 4의 response_synth로 쓰였습니다.

def get_api_query_engine_tool(document, callback_manager) -> QueryEngineTool:
    polygon_io_tool = get_polygon_io_sec_tool(document)
    llm = Settings.llm.model_copy(update={"callback_manager": callback_manager}, deep=True)
    agent = OpenAIAgent.from_tools(
        [polygon_io_tool],
        llm=llm,
        callback_manager=callback_manager,
        system_prompt=f"You are an agent that is asked quantitative questions about a SEC filing named {doc_title} ...",
    )
    return QueryEngineTool.from_defaults(query_engine=agent, name=tool_metadata.name, description=tool_metadata.description)
  • 흥미로운 점: 문서 하나당 미니 에이전트를 하나씩 새로 만듭니다. 이 미니 에이전트는 도구를 딱 하나(polygon.io 도구)만 가진 작은 OpenAIAgent입니다.
  • QueryEngineTool.from_defaults(query_engine=agent, ...) — 여기가 재미있는 부분인데, 에이전트(Agent) 자체를 QueryEngineTool로 감쌉니다. LlamaIndex의 Agent는 BaseQueryEngine 인터페이스를 구현하고 있어서 "쿼리 엔진처럼" 취급할 수 있습니다. 그래서 파일4의 quantitative_question_engine(SubQuestionQueryEngine)이 이 "에이전트를 감싼 쿼리엔진"을 부품으로 사용할 수 있는 것입니다.

콜백 → SSE 브릿지

backend/app/chat/messaging.py

LlamaIndex 내부에서 일어나는 일(서브 질문, 도구 호출)을 실시간으로 프론트엔드에 중계하는 파일. LlamaIndex의 콜백 시스템과 파이썬 asyncio 스트림을 연결합니다.

class ChatCallbackHandler(BaseCallbackHandler):
    def __init__(self, send_chan: MemoryObjectSendStream):
        ignored_events = [CBEventType.CHUNKING, CBEventType.NODE_PARSING]
        super().__init__(ignored_events, ignored_events)
        self._send_chan = send_chan

    def on_event_start(self, event_type, payload=None, event_id="", **kwargs) -> str:
        asyncio.create_task(self.async_on_event(event_type, payload, event_id, is_start_event=True, **kwargs))

    def on_event_end(self, event_type, payload=None, event_id="", **kwargs) -> None:
        asyncio.create_task(self.async_on_event(event_type, payload, event_id, is_start_event=False, **kwargs))
  • BaseCallbackHandler — LlamaIndex가 정의한 콜백 인터페이스. 이걸 상속하면 on_event_start/on_event_end가 인덱싱, 검색, LLM 호출, 서브 질문 생성 등 모든 내부 단계마다 자동으로 호출됩니다 (옵저버 패턴).
  • ignored_events = [CHUNKING, NODE_PARSING] — 청크 분할처럼 너무 자주/시시콜콜하게 발생하는 이벤트는 무시하도록 필터링. 안 그러면 이벤트 폭탄으로 SSE가 스팸이 됩니다.
  • on_event_start/end가 동기 함수인데 내부에서 asyncio.create_task(...)로 비동기 작업을 백그라운드로 던지는 이유: LlamaIndex의 콜백 인터페이스 자체는 동기(sync) 함수로 정의되어 있지만, 우리가 실제로 하고 싶은 작업(SSE로 전송)은 비동기 I/O이기 때문에 이렇게 "동기 콜백 안에서 비동기 태스크를 fire-and-forget으로 발사"하는 우회를 씁니다.
async def handle_chat_message(conversation, user_message, send_chan):
    async with send_chan:
        chat_engine = await get_chat_engine(ChatCallbackHandler(send_chan), conversation)
        ...
        streaming_chat_response = await chat_engine.astream_chat(templated_message)
        response_str = ""
        async for text in streaming_chat_response.async_response_gen():
            response_str += text
            await send_chan.send(StreamedMessage(content=response_str))
  • ChatCallbackHandler(send_chan)를 만들어 get_chat_engine()(파일 4)에 넘겨줍니다 → 파일 4에서 이 핸들러가 CallbackManager([callback_handler])로 감싸져 에이전트/쿼리엔진 전체에 배선됩니다.
  • chat_engine.astream_chat(message) — OpenAIAgent의 스트리밍 채팅 메서드. 이 호출이 파일4에서 조립한 전체 파이프라인(에이전트→서브질문엔진→도구)을 실제로 실행시키는 트리거입니다.
  • async for text in streaming_chat_response.async_response_gen() — LLM이 토큰을 생성할 때마다 text 조각이 넘어옵니다. response_str에 누적한 뒤 매번 send_chan.send(...)로 SSE 채널에 흘려보냅니다 (그래서 프론트엔드 화면에 타이핑되듯 답이 나타남).
  • send_chan/recv_chan은 LlamaIndex가 아니라 anyio의 메모리 스트림입니다 — "이 함수(생산자)"와 "SSE 응답을 만드는 함수(소비자, 파일8)" 사이의 파이프라인 역할.

  • send_chan, recv_chan = anyio.create_memory_object_stream(100) — 파일7의 handle_chat_message가 쓸 "보내는 쪽(send_chan)"과, 여기서 SSE로 내보낼 "받는 쪽(recv_chan)"을 만드는 파이프. 100은 버퍼 크기(백프레셔 방지).
  • asyncio.create_task(handle_chat_message(...)) — 파일7의 전체 파이프라인(에이전트 실행 포함)을 백그라운드 태스크로 시작합니다. 이 태스크가 실행되는 동안 아래 async for 루프가 그 결과를 소비합니다.
  • async for message_obj in recv_chan — LlamaIndex 파이프라인에서 토큰/이벤트가 도착할 때마다 DB용 Message/MessageSubProcess 객체를 갱신하고 yield로 SSE 프레임을 하나씩 내보냅니다. 이 yield가 실제로 프론트엔드 브라우저에 도달하는 데이터입니다.
  • EventSourceResponse(event_publisher()) — FastAPI(정확히는 sse_starlette) 유틸로, 위 async generator를 Server-Sent Events HTTP 응답으로 감싸줍니다. 이게 이 앱의 최종 HTTP 응답점입니다.
  • 이 함수 자체는 LlamaIndex를 직접 호출하지 않습니다 — LlamaIndex 관련 로직은 전부 handle_chat_message(파일7) 뒤로 위임되어 있고, 이 파일은 순수하게 "HTTP ↔ 내부 파이프라인 배선" 역할만 합니다.
9

오프라인 인덱스 구축 배치

backend/scripts/seed_storage_context.py

서버가 뜨기 전에, DB에 등록된 모든 문서를 미리 인덱싱해서 S3/Postgres에 저장해두는 CLI 스크립트. 실제 채팅 요청 시 인덱싱 지연이 없도록 하는 사전 준비 작업입니다.

async def async_main_seed_storage_context():
    fs = get_s3_fs()
    async with SessionLocal() as db:
        docs = await crud.fetch_documents(db)
    callback_manager = CallbackManager([])
    for doc in tqdm(docs, desc="Seeding storage with DB documents"):
        await build_doc_id_to_index_map(callback_manager, [doc], fs=fs)

def main_seed_storage_context():
    asyncio.run(async_main_seed_storage_context())

if __name__ == "__main__":
    Fire(main_seed_storage_context)
  • 파일4에서 정의한 바로 그 함수 build_doc_id_to_index_map()을 그대로 재사용합니다 — 즉 "실시간 채팅 시 인덱스를 로드/생성하는 로직"과 "배치로 미리 인덱스를 만드는 로직"이 코드 중복 없이 하나의 함수를 공유합니다. (앞서 4-4에서 배운 "없으면 만들고 있으면 로드한다" 로직이 여기서도 그대로 작동)
  • callback_manager = CallbackManager([]) — 빈 콜백 매니저. 배치 스크립트는 SSE로 뭔가를 스트리밍할 필요가 없으니 콜백 핸들러를 하나도 등록하지 않습니다.
  • Fire(main_seed_storage_context) — 구글의 python-fire 라이브러리로, 이 함수를 커맨드라인에서 python seed_storage_context.py로 바로 실행 가능한 CLI로 만들어줍니다.
  • 이 스크립트를 먼저 이해하고 나면, 파일4의 build_doc_id_to_index_map이 "실시간 요청 경로"와 "배치 인덱싱 경로" 양쪽에서 재사용되는 공용 진입점이라는 게 명확해집니다.
전체를 관통하는 3가지 LlamaIndex 패턴 요약
  1. Settings 전역 설정 — LLM/임베딩/청크 전략을 한 곳에 등록하면 이후 모든 인덱스·쿼리엔진이 암묵적으로 상속받는다.
  2. 무엇이든 Tool로 감쌀 수 있다 — 벡터 쿼리엔진(QueryEngineTool), 파이썬 함수(FunctionTool), 심지어 다른 에이전트까지 전부 같은 Tool 인터페이스로 감싸져서 상위 에이전트가 선택·호출할 수 있다.
  3. 도구는 계층적으로 쌓을 수 있다 — SubQuestionQueryEngine도, Agent도 결국 QueryEngineTool로 감싸질 수 있으므로, "에이전트 안에 쿼리엔진, 쿼리엔진 안에 에이전트"처럼 임의 깊이로 조합 가능하다.
